# iOS 启动与菜单响应排查

日期：2026-10-08。

## 调用链与发现

- `App -> LibraryPersistence -> loadLibrarySnapshot -> LibraryReadyGate -> AppNavigator -> BookshelfScreen`。书架恢复成功后才开放导航，避免用户操作空状态覆盖旧数据。当前模拟器元数据约 3.4 KB，6 本书；10 MB 本地书正文按书懒加载，正常启动不读取它。旧格式数据仍需完成一次迁移。
- `App -> WebViewFetcher` 原来无任务也挂载 WKWebView，产生不必要的原生浏览器初始化。它虽不可见且不接收触摸，初始化仍与首屏争用资源。
- `AppNavigator` 原来把所有 Screen 的组件引用交给导航配置，启动渲染时会加载未进入页面的模块及依赖。底部 Tab 原本已经懒挂载，但未等同于延迟模块求值。
- `BookshelfScreen` 恢复后立即调用 `useCheckFollowedBooks({ cacheNewChapters: true })`。只要一本书当天未检查，就会检查全部追更书；返回目录后可读取整本章节 JSON，并自动抓取新章、重写缓存。这些同步解析/序列化与菜单 Pressable 的事件处理和导航渲染共用 JS 线程。
- 网络等待本身不阻塞 JS；较重的响应处理和原生初始化可能延迟点击与页面绘制。当前模拟器没有开启追更，不能把该风险认定为用户设备上卡顿的唯一原因。
- 启动图固定等待 520 ms，再用 220 ms 淡出，属于现有展示时长。其 `pointerEvents="none"` 不拦截菜单触摸。

## 优化

1. 导航页面改用稳定的 `getComponent` 函数，首次进入页面时加载对应模块。
2. 隐藏抓取器只注册轻量桥接，首个实际请求才加载 WebView 模块并创建原生实例。之后保持实例，继续复用 Cookie。同步锁定领取的任务，修复多个挂载前缓冲请求覆盖队首的问题。
3. 自动追更等书架恢复、聚焦至少 1.5 秒并收到 idle 回调后才启动；离开书架取消尚未开始的任务。开始后的检查只运行一次，页面卸载不提交迟到 UI 状态。
4. 自动追更只检查当天尚未尝试的有效追更书，取消启动后自动下载正文。手动检查仍检查全部追更书并缓存新章，阅读时仍按需缓存正文。
5. 正式包不在启动路径加载开发自测组件。保持书库恢复门禁、原有磁盘格式及失败重试保护。

## 验证边界

- 没有真机 CPU/FPS/触摸延迟采样，也没有可信的优化前后毫秒对比，不报告启动提升百分比。
- 当前模拟器未开启追更；追更调度、过滤与正文缓存边界由自动测试验证，不冒充真实书源更新验收。
- 延迟加载会把页面模块的首次求值移到首次进入时；后续复用模块缓存。
- 极大的书架元数据、旧格式首次迁移、超大书架一次性渲染以及已开始请求的目录解析仍可能耗时，本次没有把所有同步工作迁到后台线程。
